# 群旁听回复发送错误修复 0.22.34

## 根因

用户反馈群内不接话。只读检查确认两个现有群均已启用；一个是正常档、自适应接话，另一个是活跃档、原有正常 Agent 路由。participation.mode 未配置时的 off 是新参与决策路由的关闭状态，不是群友模式总开关，不能据此解释所有群沉默。

正常档群持续收到真实消息，记录中既有“本轮选择倾听”，也有“接话未确认成功（ReferenceError）”。追踪旁听发送路径，发现调用 stripFinalChineseFullStop 时没有从 voice.js 导入；模型决定回复后会在格式化正文阶段抛出 ReferenceError，尚未进入平台发送。活跃档群的证据记录则没有当天的新入站，不能据此判断该群发送链路故障或消息被忽略。

## 修复尝试与验证

本轮只有一次业务修复：补齐 group-participation.js 的缺失导入，不改变两个群的开关、频率、权限、TTL、参与模式或 NO_REPLY 行为。去掉正文句尾中文句号的既有需求保留。

先增加隔离用例，通过实际 groupParticipationGate、定时评估、模型适配器、格式化、发送边界和本地回执状态运行；模型与平台发送器均为模拟，不连接真实 QQ。修复前稳定复现相同 ReferenceError，模型已生成但发送次数为零。补齐导入后两条模拟短消息均正确去除句尾句号、保留句中标点，并写入 accepted 状态。

首次修复后核验在 Windows 清理夹具时出现 EPERM：withQQIdentity 打开的证据库单例未关闭。使用现有 closeQQEvidence 释放夹具后再删除临时目录，不修改业务代码规避该问题。最终 40 个文件、444 项离线合成核验通过，失败 0。这不是实际群发送测试。

## 发布与真实验收边界

构建 0.22.34 插件及规范化 profile 锁，部署前备份 0.22.33 包、运行插件、版本和活动 profile 清单/锁文件，按受管理脚本重启。核对源码、运行副本和活动安装的 81 个插件文件；保留 0.22.33 已验证的 TLS 和文件路由修复。

修复后的真实群非 @ 接话回执仍待新入站观察；不能用离线发送器或健康检查声称实际群聊恢复。正常档仍可能按场景选择倾听或因过期、频控取消发送。另一群缺少新入站的原因没有充分证据，不改映射或扩大允许群。
